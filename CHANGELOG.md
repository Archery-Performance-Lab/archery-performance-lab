## [Unreleased]

### Fixed

- `scripts/lib/render-skeleton-overlay-svg.cjs` (and the inline copy in `tools/posture-video-player.html`): the skeleton overlay's line thickness, dot radius, and font sizes are fixed pixel values defined in the SVG's own viewBox space — which equals the source media's native resolution, not its on-screen CSS display size. That was invisible for video frames (~1080px wide, close to what these sizes were tuned against) but direct report on a real high-resolution photo (3213px wide): lines "molto sottili", marker dots "diametro ridotto", labels "molto piccole" — a ~3x-higher-resolution source squeezed into the exact same CSS display box shrinks every fixed-size element roughly 3x further than a typical video frame does. Fixed by scaling every visual size (line stroke-width, dot radius/stroke-width, label font-size, `angleLabelMarkup()`'s and `zoneBoxMarkup()`'s font sizes/stroke-widths/box dimensions) by `visualScale = max(1, widthPixels / 1080)`, computed once in `renderSkeletonOverlaySvg()` and threaded through — floored at 1 so a lower-resolution source never renders thinner than today's already-correct video appearance, only ever scales up for something larger. Verified directly: at the 1080px reference width, sizes are unchanged (stroke 2.0, dot radius 6.0); below it (400px), still floored to the same reference sizes; at 3213px, both scale to ~2.97x (stroke 5.95, dot radius 17.9) as expected. Kept in sync between both copies. All 80 tests pass (no TypeScript source touched — this is pure SVG-rendering logic in the two `.cjs`/inline-script copies).

### Changed

- `posture-analysis/metrics.ts`'s `drawArmElbow` entry in `DEFAULT_POSTURE_METRICS` gets a new `idealRangeDegrees: [1, 15]`, overriding ghiggo's originally-ported `[25, 40]` on direct request — the first time an already-ported ghiggo range has been overridden rather than a new metric's range set for the first time. `warnRangeDegrees` follows the same convention already established for an unspecified warn range: ±12° around the new ideal range's own center (8°, giving `[-4, 20]`), rather than keeping the old `[10, 50]` warn range, which was built around the previous ideal and no longer made sense next to the new one. `posture-video-player.html`'s inline copy updated to match and verified identical via Node's `vm` module against the compiled TypeScript. No test changes needed — the existing `drawArmElbow` test fixture (a 90°-bent elbow) still lands outside both the old and new ranges, so it still asserts `"outOfRange"`. All 80 tests pass.

- `posture-analysis/metrics.ts`'s `footStanceAngle` entry in `DEFAULT_POSTURE_METRICS` gains a real default `idealRangeDegrees: [-2.5, 4.0]` — a direct request, not ported from any reference implementation the way the other six ranges are, but a deliberately-given value rather than an invented one. `warnRangeDegrees` was not separately specified, so it defaults to ±12° around the ideal range's own center (0.75°, giving `[-11.25, 12.75]`) — the same tolerance `posture-video-player.html`'s "Cattura come ideale" already uses around a single captured value, applied here to a given range's midpoint. The metric now classifies as ok/warning/outOfRange like the other six instead of always reporting a `null` status; the `null`-range mechanism itself (`evaluatePostureMetric()` returning `null` for an uncalibrated metric) is unchanged and still reachable by clearing a range in the "Soglie" panel. `posture-video-player.html`'s inline copy of `DEFAULT_POSTURE_METRICS` updated to match and verified identical via Node's `vm` module against the compiled TypeScript. Tests updated: `evaluatePostureMetric`'s "no configured ranges" case now uses a synthetic definition instead of `footStanceAngle` (which no longer has one by default), plus a new test asserting `footStanceAngle`'s own default classifies correctly; `computeMetricScorePercent`/`computePostureScorePercent`'s "excluded: no ranges" cases likewise switched to a synthetic uncalibrated definition. All 80 tests pass.

### Added

- `tools/overhead-alignment-video-player.html`: a video "player" version of `tools/overhead-alignment.html`, for the same real coaching check (Filippo Clini's manual, checked directly rather than guessed at: the forearm-arrow alignment line must hold "sia se osserviamo l'atleta frontalmente, sia nella vista dall'alto") but stepping through a real overhead-framed video instead of one hand-picked still photo, so pretrazione and trazione can be compared within a single real shot. Direct request after two false starts on automating Drawing-phase detection instead: first, deriving it from the existing wrist-to-face distance signal turned out too noisy on real footage to threshold reliably (even smoothed, real net change during a genuine pull was too close to BlazePose's own frame-to-frame position noise — see the now-removed attempt below); second, a proposed bowstring-linearity signal was correctly ruled out before being built further — a string of any color can be confused with the background, and more fundamentally the real coaching check the user described isn't about the string's own shape at all, but a hand-in-grip and elbow-to-pivot-point alignment a technician actually looks for. That check needs an overhead camera, an angle BlazePose's real-world accuracy has never been verified against (this package's own established limitation — frontal/rear framing works, other angles mislead automatic detection), which is exactly why `manual-annotation/` and `tools/overhead-alignment.html` already exist and why this new tool stays manual too rather than trying to automate an unverified angle. No TensorFlow/CDN dependency at all — this tool never runs pose estimation. Points are stored **per frame** (`{ timestampMs, points }`, matched within a small tolerance rather than an exact key, since repeated `<video>` seeks to "the same" requested time don't always land on the identical millisecond); requests stay **global**, so a coach reusing the same point names (e.g. `gomito_corda`, `mano_arco`) across frames gets the same computed check automatically everywhere those names exist. A "Copia punti dal fotogramma precedente" button copies the nearest earlier frame's points as a starting point to drag/re-click-correct, since re-placing several points by hand on every single frame is real friction the single-image tool never had — explicit and opt-in, never automatic. Export shape extended to `{ requests, framesByTimestampMs, videoFileName, ... }` (never the video itself); `scripts/compute-annotated-angles.cjs` now reads both this shape and the original single-image `{ points, requests }` one, telling them apart by which of `points`/`framesByTimestampMs` the file actually has, and prints one authoritative result block per annotated frame for the video case. Verified for real, not just read-and-reasoned-about: loaded a real overhead-framed video the user provided (2160x3840, 13.46s) in a live browser tab, stepped frames via the actual UI (confirmed the millisecond counter advances by exactly the configured step), placed points on a real mid-video frame, and confirmed via `getImageData` (not just eyeballing — at this resolution a 5px marker is close to invisible on screen at the page's own display scale) that markers land at the exact requested pixel coordinates; computed a real `angleAtJoint` result (115.71°) that matched exactly between the page's live preview and `compute-annotated-angles.cjs`'s authoritative path run against the real exported JSON; export/import round-tripped correctly; the original single-image JSON shape still works unchanged. What this verification does **not** cover: whether the alignment numbers this tool would report on a real pre-draw-vs-draw comparison actually match what the manual describes as correct/incorrect — that needs a coach's own judgment on real footage, same as every other calibration step in this package. HTML tag balance checked, inline script confirmed to parse as valid JavaScript.

- `posture-analysis/metrics.ts`: `computeMetricScorePercent()` and `computePostureScorePercent()` — a continuous 0-100 "how correct is this position" score, backing a new circular gauge shown below the metrics table in `tools/posture-video-player.html`, updating live every frame. Per-metric score is 100 inside `idealRangeDegrees`, falls linearly to 50 at the `warnRangeDegrees` edge, then continues that slope to 0 one more warn-band-width further out (no cliff at the warn boundary). The overall score averages only metrics that are actually scorable in the current frame — a metric with a missing keypoint or with no configured ranges yet (`footStanceAngle` before calibration) is excluded from the average rather than scored 0, so undetected camera coverage isn't indistinguishable from a genuinely bad position; returns `null` (shown as gray "n/d") when nothing is scorable. Explicitly documented as a UI presentation choice, not a validated coaching score — no reference implementation exists to port a "correct" curve shape from, unlike `DEFAULT_POSTURE_METRICS`' six ported ranges. `posture-video-player.html` duplicates both functions plus a new `renderScoreGaugeSvg()` (two-circle SVG donut, color-coded green/orange/red at the same ≥80/≥50/<50 thresholds the metrics table already uses). Verified: 10 new unit tests (falloff at hand-computed points on both a one-sided range and a range whose warn band sits below ideal, plus the no-warn-band-on-one-side and exclusion/`null` cases), all 79 tests pass; the inline HTML copy was checked via Node's `vm` module against the same points and a synthetic 7-keypoint frame's full aggregate score, matching the compiled functions exactly; manually exercised in a real browser tab with injected synthetic frames to confirm all four gauge states (green/orange/red/gray "n/d") render correctly; HTML tag balance checked.

- A real correction to Release detection strategy, recorded in `types/phase.ts` and `README.md`. The slow-motion Kim Woojin clip first led to a plan to require audible clicker sound in future calibration videos, on the idea that the clicker's audio could become the primary Release signal (the wrist-velocity fallback `phase-detection/` currently relies on had just been shown too noisy to trust, even after the warmup-exclusion fix, since BlazePose's tracking gets intermittently confused whenever the draw-side hand stays close to the face for a long hold, not just at the start of a clip). Coach input corrected this: a real technical analysis is filmed from the side opposite the clicker, so an instructor never actually listens for or watches the clicker fall — they watch the string-hand fingers, judging whether the fingers open involuntarily (correct — pushed open by the string) versus voluntarily (a technical fault). The clicker-audio requirement is withdrawn. This surfaces a genuine, still-open limitation rather than a solved one: BlazePose's 33-keypoint model has no individual finger joints, so the actual coaching criterion for Release isn't observable from the current pose model at all.
- Further coach detail on the Release string-fingers criterion, added to `types/phase.ts`: the back of the hand must show no tension, the string sits between the first and second phalanx of the fingers used, and at Release the fingers stay relaxed and curved toward the neck rather than opening outward. Two real draw techniques recorded, not conflated: three-finger (index/middle/ring, ring sometimes only resting) and a genuine two-finger draw (index/middle only, ring not used) — neither is "the" correct one. Also a real correction to the entry immediately above: hand tension is *not* unobservable from video after all — a tensed hand visibly shows its tendons standing out under the skin, no contact or finger-level tracking required. It's still not something BlazePose's keypoint model captures (that would be image/texture analysis on the hand region, a genuinely different computer-vision technique from pose estimation), so the underlying limitation stands, but the earlier framing ("not observable from any video") overstated it.
- `hand-tension/` module: `computeCropRegionAroundKeypoint()` (a shoulder-width-relative crop region centered on a keypoint, clamped to frame bounds), `cropFrameRegion()`, `computeHandTensionMetric()` (variance of a Laplacian response over the cropped region — a standard, explainable texture/edge-density measure, not a learned model). A candidate proxy for the tendon-visibility observation above. Completely unvalidated so far — `scripts/inspect-hand-tension.cjs` computes it frame by frame around the draw-side wrist and prints the highest/lowest values with timestamps, to be checked against what the real video shows before trusting it for anything. Fully unit-tested, including an exact hand-computed Laplacian-variance expected value for a known synthetic input.
- `shot-analysis/analyzeShotVideoWithFrames()`: the same pipeline as `analyzeShotVideo()`, but yields each frame's pixel tensor alongside its `PoseFrame` instead of disposing it internally — needed by `hand-tension/`, which requires the actual image, not just keypoint positions. Disposal is left to the caller, same ownership rule `extractFramesFromVideo()` itself already follows.
- `scripts/lib/render-svg-line-chart.cjs`: a small, dependency-free SVG line-chart generator (plain string-building, no charting library) — a shared helper for calibration scripts, not part of `@apl/video-analysis`'s public API.
- `scripts/inspect-elbow-angle.cjs`: batch-computes the draw arm's elbow bend angle (shoulder-elbow-wrist, via the existing `biomechanics/angleAtJointDegrees()`) frame by frame for every calibration video and renders it as an SVG chart over time, alongside a per-frame CSV. Prompted by an out-of-context suggestion (from an unrelated chat) to use Python + MediaPipe + OpenCV for this kind of analysis — MediaPipe and this project's BlazePose are the same underlying pose model family, so the signal was sound, it just didn't warrant a second language/runtime in this monorepo. Reuses the same 300ms warmup-exclusion and per-video try/catch pattern already established in `detect-phases.cjs`/`build-calibration-dataset.cjs`.
- `biomechanics`: two new pure geometry primitives, `angleFromHorizontalDegrees()` (how far a line between two keypoints deviates from level, folded into [0°, 90°]) and `tiltFromVerticalDegrees()` (how far a line deviates from plumb-vertical). Both ported line-for-line from a real, working third-party reference implementation (see `posture-analysis` below), not invented independently.
- `posture-analysis` module: `analyzePosture()` computes six postural checks from a single `PoseFrame` — shoulder level, hip level, bow-arm elbow angle, draw-arm elbow angle, head tilt, torso verticality — each classified `"ok" | "warning" | "outOfRange"` against configurable ranges (`DEFAULT_POSTURE_METRICS`), or `null` when a required keypoint is missing/low-confidence rather than a misleading default. Directly ported (keypoints, formulas, and the default ideal/warning ranges) from "Archery Posture Tracker" (ghiggo.altervista.org/posture), a real third-party browser tool built on MediaPipe Pose — its plain, unminified client-side JavaScript source was read directly, not reverse-engineered from watching it run. `DEFAULT_POSTURE_METRICS` is explicitly documented as a real, working starting point copied from that tool, not something calibrated against this project's own footage — that reference tool itself treats its defaults the same way, rebuilding them from a captured real position via its own "Cattura" feature rather than trusting a universal number.
- `scripts/lib/render-skeleton-overlay-svg.cjs`: renders the skeleton (connecting lines + keypoint dots, confidence-aware so a partial/lateral view naturally yields a partial skeleton), the two elbow-angle readouts, and dashed shoulder/hip alignment boxes as a plain SVG string — ported from the same reference tool's canvas drawing logic. `scripts/lib/render-posture-overlay-html.cjs` wraps one extracted frame image and that SVG into a standalone `.html` file (image and SVG stacked via `position:absolute`, both stretched to the same container so they stay pixel-aligned at any zoom level), plus a metrics table — opens directly in a browser, no new dependency.
- `scripts/inspect-posture.cjs [videoFilePath] [right|left] [timestampMilliseconds]`: single-video, single-frame posture overlay tool tying the above together — extracts one frame as a real JPG (frame-accurate `-ss` placement), computes the six metrics, and writes one `.html` file. Defaults to the slow-motion Kim Woojin video and the midpoint of its duration. Follows this package's established pattern of proving a new, unvalidated capability on one real frame/video before batching it.
- `scripts/inspect-posture.cjs` now also prints every keypoint's raw `confidenceScore` and pixel position to the console. Added after the very first real end-to-end run (real Mac, real BlazePose, real footage — see README.md): the rendered skeleton visually disagreed with the photo for the draw-arm joints and the hips, while every posture metric still reported "OK". Before guessing at a fix (e.g. just raising the confidence threshold), this is the data needed to tell apart two different problems — a genuinely low `confidenceScore` the 0.5 threshold should have already caught, versus BlazePose confidently reporting a wrong position for an occluded/out-of-frame joint, which no threshold adjustment fixes. Not yet diagnosed which one this is — see README.md's "Known open question" note.
- **Continuous video tracking**, replacing the single-frame posture-overlay workflow above rather than patching it further, after it became clear (see "Fixed" below) that picking one representative timestamp was the wrong task in the first place — a real coach reviews the whole action continuously, not one still frame. `scripts/build-posture-timeline.cjs [videoFilePath] [right|left] [framesPerSecondToExtract]` runs pose estimation and `analyzePosture()` across an entire video and writes every frame's keypoints and posture results to one JSON file — deliberately without the usual 300ms warmup-exclusion filter, so a human reviewing it can see exactly where/how detection gets unstable instead of having it hidden. `tools/posture-video-player.html` plays the original video back with the skeleton/angles/alignment boxes drawn live on top, synced to real video frames via `requestVideoFrameCallback`, plus frame-by-frame step buttons for finding a specific moment by eye with the overlay already visible. `scripts/lib/render-skeleton-overlay-svg.cjs` gained a small dual-environment guard (`module.exports` only runs where `module` exists) so this new page can load it directly via a plain `<script src="...">` tag — the exact same code serving both Node scripts and this static page, verified by running the file through Node's `vm` module with no `module` global defined (a real simulation of a browser `<script>` tag, not just an assumption).
- `biomechanics`: `angleBetweenLinesDegrees()` — angle between two arbitrary line segments that do not share a vertex (unlike `angleAtJointDegrees()`), folded to [0°, 90°]. Needed for a real coaching check (forearm-vs-arrow-line alignment, from Filippo Clini's manual) whose two lines don't meet at a common point.
- `manual-annotation` module: `computeAnnotatedAngles(points, requests)` — the same kind of angle/distance checks as `posture-analysis`, but computed from points a human places by hand on a still photo instead of from BlazePose keypoints. Exists specifically for the manual's overhead-view alignment triangle (bow hand / draw elbow / head, plus the forearm-to-arrow line): that check needs a camera positioned directly above the archer, an angle BlazePose's real-world accuracy has never been checked against, so rather than guess whether automatic pose estimation would even work there, a coach places the points themselves — the same way the manual's own reference photos were annotated. Deliberately generic (named points, named requests — `angleAtJoint`, `angleFromHorizontal`, `tiltFromVertical`, `angleBetweenLines`, `distance`), not hardcoded to that one triangle. Delegates to the exact same tested `biomechanics/` primitives BlazePose keypoints use; a request referencing a missing or coincident point produces an `error` result instead of throwing, so one mistyped name does not discard the rest of a batch.
- `tools/overhead-alignment.html`: a standalone, dependency-free HTML page for placing those points and building those requests interactively — upload an image, click to place/name points, pick points from dropdowns to build requests, see a live preview, export as JSON. No image ever leaves the machine (plain `FileReader`/`<canvas>`, no upload, no server). Its live preview duplicates the geometry formulas by hand in plain JS (a static HTML file with no build step cannot import from this TypeScript package) — verified node-side to produce identical results to the real primitives on the same test cases used in the unit tests, but documented in the file itself as a convenience preview, not the authoritative answer.
- `scripts/compute-annotated-angles.cjs <jsonFilePath>`: reads the JSON exported by the HTML tool above and calls the real, tested `computeAnnotatedAngles()` — the actual authoritative computation, kept deliberately separate from the interactive point-placing UI.

### Changed

- `Arrow.spine: number` replaced with `Arrow.staticSpine: StaticSpineMeasurement`, to keep the measurement standard and units explicit rather than a bare number.
- `@apl/video-analysis`'s pose-estimation backend switched from `@tensorflow/tfjs-node` (native bindings) to the WASM backend: tfjs-node's native "tensorflow" backend does not implement several image-preprocessing kernels BlazePose needs (`Transform`, `RotateWithOffset`, `FlipLeftRight`) — a long-standing, unresolved upstream gap, not fixable from this package. The WASM backend implements the full kernel set and has no compiled native addon, so it is also portable across the OS/CPU architecture that ran `pnpm install`.
- `ShootingPhase` taxonomy reviewed and corrected against real coaching methodology: first with Tommaso Franchini (FITARCO first-level coach, tessera 151218), then cross-checked against a written manual by Filippo Clini (Italian national team coach, "Livello Avanzato per l'istruttore di tiro con l'arco"). Widened `Stance` to full-body posture including head stillness, and added `PreDraw`, `Aiming` and `Expansion` as their own phases rather than folding them into `Drawing`/`Release`. `Release` is documented as not directly observable from body pose alone (BlazePose tracks landmarks, not the arrow tip/clicker) — detection should primarily use the video's audio track, falling back to a string-arm velocity spike. `Nocking` was dropped first (no single correct technique to evaluate against), then re-added after Clini's manual treated it as a real checkpoint — not for a fixed form, but for the archer's own *consistency* under competition stress. `SetUp` (string-hand finger position and bow-hand grip, before the arms are raised) was added directly from Clini's manual as a distinct phase between `Nocking` and `PreDraw`.

### Fixed

- `tools/posture-video-player.html`'s new in-browser automatic processing (see "Added" above) initially used `modelType: "full"`, matching `pose-estimation/detector.ts`'s Node-side choice. First real test against a real archer video (the user's own footage, loaded directly through the page) showed no skeleton overlay at all — just plain video playback. Diagnosed against that same real video, not guessed at: every processed frame produced a structurally valid pose object (`posesLength: 1`) whose every keypoint AND top-level score were `NaN`. Reproduced identically on both the WebGL and CPU backends (ruling out a GPU/software-rendering precision issue) and identically against both the raw `<video>` element and a `<canvas>` snapshot of the exact same frame (ruling out a video-element-specific decoding issue) — narrowing it to the `"full"` model graph itself, in this exact CDN-loaded `pose-detection@2.1.3` + `tfjs@4.22.0` combination. Both `"lite"` and `"heavy"` were then confirmed, against that same real frame, to return real pixel coordinates and confidence scores (0.999+). Fixed by switching to `modelType: "heavy"` — more accurate than `"full"`, not less, and consistent with this project's own already-stated preference for offline video analysis over live-camera speed (`pose-estimation/detector.ts`'s own doc comment on why it picks `"full"` over `"lite"` in Node) — confirmed fast enough in practice (~60ms/frame measured on WebGL in this same real test, vs. ~30ms for `"lite"`, both comfortably interactive for offline processing). This is a `"full"`-modelType-specific bug in this library version combination, not a "BlazePose doesn't work in a browser" problem — `"lite"` and `"heavy"` both work correctly.

- Immediately after the fix above shipped, a second real bug surfaced on the very next real test: the user processed a second video in the same tab session and got the exact same symptom (`NaN` everywhere, no skeleton) despite `"heavy"` already being in place. Diagnosed by direct A/B comparison against the same real video frame: the page's own memoized detector (`ensurePoseDetector()`, created once per page load and reused across every file processed in that session) reliably returned `NaN`, while a brand-new `poseDetection.createDetector()` call, immediately afterward, against that identical frame, reliably returned real coordinates — repeated across several separate detector instances with consistent results in both directions. What specifically makes a given `createDetector()` call come out degenerate was not pinned down (varying `modelType`, backend, `tf.ready()` call timing, and video-vs-canvas input all failed to reproduce it in isolation once isolated from a previously-memoized instance), but "was this detector reused from an earlier file" was the one reliable common factor across every failure and success observed. Fixed two ways: (1) `ensurePoseDetector()` is replaced by `createFreshPoseDetector()`, which creates a brand-new detector for every file processed rather than memoizing one for the whole page session — still reused across every frame within one file's own extraction loop (confirmed safe over repeated calls, several frames deep, against a non-degenerate instance), just never carried over to the next file. (2) A new `isDegeneratePoseFrame()` check (NaN on the first keypoint despite a non-empty keypoints array — a real "nothing detected" frame comes back with an empty array instead, so this cannot false-positive on a genuine low-confidence result) runs after every frame's estimate in both `processImageFile()` and `processVideoFile()`; on a degenerate result, one retry with another freshly created detector is attempted before giving up with a clear, visible error message instead of silently completing with a "Completato" status over data that was actually all garbage — the exact misleading outcome the user hit both times.

- The fix above (per-file fresh detectors) reduced but did not eliminate the NaN bug — the very next real video still failed, including after a full page reload and reselecting the file. This time the root cause was found and confirmed, not just narrowed down: a GPU memory leak. `tf.memory()` showed 26,268 live tensors and ~2.94GB of allocated GPU memory in a tab that had (over one extended debugging session) created roughly twenty `PoseDetector` instances, none of them ever disposed — each one holds its own copy of BlazePose's model weights as WebGL textures, and `PoseDetector.dispose()` (a real method this library exposes) is required to free them; nothing does this automatically. With that much leaked GPU memory, calling the exact same code against the exact same real video frame was directly observed to non-deterministically succeed (real coordinates, 0.999+ confidence) or fail (NaN everywhere) from one call to the next — confirmed by disposing one detector and watching `tf.memory()`'s tensor count actually drop. This explains why earlier diagnosis attempts kept finding a "fresh detector" recovers the bug and a "reused" one doesn't: a genuinely fresh detector, tested in isolation early in a session, had little leaked memory competing with it yet; by the time enough detectors had accumulated, freshness stopped being the deciding factor at all (a completely new detector failed just as often as a reused one, once GPU memory pressure was high enough) — the earlier "cross-file reuse" explanation was a real, reproducible correlation at the time, but not the actual mechanism. Fixed by calling `detector.dispose()` on every detector this page creates as soon as it is done with it, in both `processImageFile()` and `processVideoFile()` (including the retry path, which now also disposes the detector it is replacing) — confirmed via a real stress test of 8 consecutive create→estimate→dispose cycles showing `tf.memory().numTensors` returning to exactly 0 after every single dispose call, no growth across repeated cycles. `isDegeneratePoseFrame()`'s retry-then-degrade-gracefully behavior (see above) is kept as a second, independent line of defense rather than removed, in case some other cause ever produces the same NaN signature again.

- With GPU memory confirmed clean (0 leaked tensors), the same real video still failed on every single frame. Final, clean, deterministic isolation: the SAME detector instance, at the SAME moment, given a `<canvas>` snapshot of a frame returned real coordinates (0.999+ confidence) every time, and given the live `<video>` element directly for that IDENTICAL frame returned NaN every time — nothing else varied between the two calls. Passing a live DOM media element directly to `estimatePoses()`, rather than a `<canvas>` snapshot of it, is unreliable in this exact library/browser combination — reading via `<canvas>` `drawImage()` forces a synchronous, fully-materialized bitmap before any WebGL texture upload, while reading directly from a `<video>` element depends on whatever this library version does internally to pull pixels from it, which evidently is not reliable. Fixed in `processVideoFile()` by drawing each frame to a reusable canvas (`frameCanvas`) before calling `estimatePoseFrameFromMediaElement()`, rather than passing the live `<video>` element to it directly.

- A fifth real bug, found on a real photo: a user-uploaded 3213x5712 image showed the skeleton positioned nowhere near the person in it (top-left area of the frame instead of centered on the archer). Not a crash and not NaN — `posesLength: 1`, confidence 0.998 — just confidently wrong coordinates, reproduced byte-for-byte identical (599.66, 536.2) across several fresh detectors called through `processImageFile()`'s real code path. Diagnosed the same way as the `<video>` bug above: the SAME detector instance, at the SAME moment, given a `<canvas>` snapshot of that exact photo returned the visually correct position (confirmed against the actual photo, not assumed) every time across 6 repeated calls, while the live `<img>` element for that identical photo returned the same wrong position every time — the `<video>`-element bug's root cause also applies to `<img>` elements, at least for a photo this large. This is a more dangerous failure mode than NaN: `isDegeneratePoseFrame()`'s NaN check cannot catch a wrong-but-plausible-looking result, so it would have shipped silently if not caught by the user actually looking at the overlay. Fixed by `processImageFile()` drawing to a canvas (`imageCanvas`) before calling `estimatePoseFrameFromMediaElement()`, exactly like `processVideoFile()`'s `frameCanvas` — this page no longer passes a live `<video>` or `<img>` element to `estimatePoses()` anywhere, only canvas snapshots.

- ACE package failed to build: wrong relative path in `tsconfig.json`'s `extends`, a stale `./calculatics` import (folder had been renamed to `./calculations`), a duplicate `GRAVITY` export causing an ambiguous-export error, empty `physics` stub modules (`drag.ts`, `force.ts`, `motion.ts`) breaking `export *`, and `constants/air.ts` re-exporting itself instead of defining `AIR_DENSITY`.
- `pnpm test` failed on a clean checkout even after `pnpm install`, in two stages: (1) `turbo`/`typescript`/`@types/node`/`prettier` were undeclared, so pnpm had nothing to install; (2) once declared, `@types/node` still wasn't picked up inside `packages/core/ace` because pnpm workspaces don't hoist a package's dependencies to its siblings — each workspace package must declare what it uses. Fixed by declaring `typescript`/`@types/node` directly on `@apl/ace`, and explicitly setting `"types": ["node"]` in its test tsconfig rather than relying on automatic `@types` discovery.
- `pnpm-lock.yaml` was a near-empty skeleton (no dependency had ever been resolved with real registry access); replaced with a fully resolved lockfile.
- `.turbo/` (Turborepo's local cache directory) was not covered by `.gitignore`.
- `detect-phases.cjs` and `inspect-slowmo-release.cjs` fed `detectShootingPhases()` raw pose frames including the pose detector's own unstable startup window — found via a real run against all 17 calibration videos, where 14 of them detected "Release" within the first ~300ms followed by an implausible "FollowThrough" spanning almost the entire rest of the clip (up to 320+ seconds in one case), because the false trigger from warmup noise stopped the detector from ever looking further into the video for the real Release. `build-calibration-dataset.cjs` already excluded this window from its own summary statistics, but `detectShootingPhases()` itself had never gone through the same filtering. Fixed at the call site in both scripts (filtering frames before the first 300ms out before detection runs), not inside `detectShootingPhases()` itself, which stays a pure function agnostic to where its input came from — its synthetic unit tests build clean sequences starting at t=0 and would break if the function silently dropped early frames.
- `scripts/build-calibration-dataset.cjs` and `scripts/detect-phases.cjs` crashed on the first unreadable/corrupt video in a calibration folder, silently discarding every result from the run — including `_summary.csv`, which is only written once, after the whole batch, so a failure partway through meant no summary at all, not just a missing row for the bad file. Both scripts now catch a per-video failure, log it, and continue with the rest of the batch; `build-calibration-dataset.cjs`'s `_summary.csv` gained a `status` column (`OK`/`FAILED`) so a skipped video is visible instead of silently missing. Found via a real corrupt file: one of the Kim Woojin match clips got truncated mid-encode by a command timeout while being extracted, producing an mp4 with no `moov atom` — re-encoded correctly and the corrupted copy replaced, but the batch-crash behavior was a real bug independent of that specific file and worth fixing regardless.
- `scripts/inspect-hand-tension.cjs` reported its highest/lowest tension readings without recording *where* the analyzed crop actually was. A first real run on the slow-motion video flagged a highest reading (243) over ten times the lowest (21) between two frames that looked visually near-identical at anchor — a real, plausible explanation is that video's background: a densely patterned sponsor banner directly behind the archer, which could dominate the Laplacian-variance metric if the crop drifts onto it even partially, since the banner has far more high-contrast edges than skin ever would. Couldn't confirm or rule this out without knowing the crop's exact position. Now logs `wrist_x_px`/`wrist_y_px`/`crop_x_px`/`crop_y_px` per frame in the CSV, and prints the crop bounds for the highest/lowest frames directly, so the exact analyzed region can be reconstructed and inspected instead of guessed at.
- Reconstructed the exact crops from those logged coordinates and found the real cause — not the background banner (that hypothesis was wrong), but the archer's own bright white shirt collar behind the hand: the high-reading crop happened to include the sharp hand/collar boundary, the low-reading crop stayed on smoother skin. **`hand-tension/`'s Laplacian-variance approach is paused, not resolved**: a real, checked-against-real-footage negative result, documented in `types/phase.ts`, `README.md` and `hand-tension/texture.ts` rather than left as an untested hope. The crop/texture primitives (`computeCropRegionAroundKeypoint`, `cropFrameRegion`, `computeHandTensionMetric`) are kept as general building blocks; this specific use of them is not something to build on as-is.
- `render-svg-line-chart.cjs`'s y-axis label was first drawn as rotated, vertical `<text>` (the conventional way to label a vertical axis). An isolated rendering test found ImageMagick's SVG delegate renders rotated `<text>` as invisible (confirmed with a minimal reproduction, not just the chart itself), which — since actual browser rendering couldn't be verified from this sandbox — was treated as too risky to ship on an unverified assumption. Changed to a plain horizontal label at the top-left of the plot area instead, removing the risk entirely rather than resting on "it probably works in a real browser."
- `scripts/inspect-posture.cjs` treated its first argument as always being a video path, unlike the two existing single-video scripts it was modeled on (`inspect-slowmo-release.cjs`, `inspect-hand-tension.cjs`), which special-case `"left"`/`"right"` as `drawSide` when no path is given. Found immediately on the real Mac: `node scripts/inspect-posture.cjs right` (the exact command this package's own README told the user to run) failed with `Video not found: .../right`, since `"right"` was resolved as a file path instead of a draw side. Fixed by adopting the same argument-parsing convention as those two scripts, so the default-video, side-only invocation actually works.
- `scripts/inspect-posture.cjs`'s ffmpeg frame-extraction command passed `-frames:1` (a malformed option: ffmpeg parsed `1` as a *stream specifier* — "apply `-frames` to stream #1" — not a frame count, then failed looking for the real count in the next argument, `-q:v`). Found on the very next real run after the argv-parsing fix above, once the script got as far as actually calling ffmpeg. Fixed to `-frames:v 1` (specifier `v` for the video stream, `1` as its own argument) — verified against a real ffmpeg invocation (a synthetic test video, same technique `verify-frame-extraction.cjs` uses) since this sandbox cannot run the actual calibration footage.
- Same command, one warning further: the real Mac's ffmpeg (6.0) warned that a plain, non-pattern output filename isn't a valid `image2`-muxer target without `-update 1`, recommending that flag for writing a single still image — harmless in this ffmpeg version (the JPG was written regardless, and BlazePose successfully processed a real frame end-to-end on the real Mac for the first time), but not guaranteed to stay a harmless warning in a future ffmpeg version. Added `-update 1` to be explicit rather than rely on that.
- Diagnosed the "known open question" the confidence-logging addition above was added to answer: it looked, from confidence scores alone, like it could be BlazePose confidently misplacing occluded draw-arm joints (0.99+ confidence, but positions that didn't match the photo). It wasn't — checked directly against the real video (not just the numbers) and found the default timestamp (`inspect-posture.cjs`'s "midpoint of video duration", picked with no knowledge of what that instant actually shows) landed *after* Release and FollowThrough had already finished, not during Anchor. The odd, tightly-bent elbow angle was an accurate reading of a hand already pulled back past the jaw, not a detection error.
- The suggested fix for the point above — read the real Anchor timestamp off `scripts/inspect-elbow-angle.cjs`'s existing per-frame chart — was itself wrong, corrected after checking the real chart rather than left standing: for this specific slow-motion video, the whole elbow-angle signal is noisy with no readable plateau, not just its first ~300ms. This is the same pose-detection instability already documented as the reason `phase-detection/detectShootingPhases()` doesn't work on this video either — it affects this angle signal too, contrary to the (wrong) assumption that a static angle would be less sensitive to it than a velocity derivative. Corrected in README.md: this video needs a timestamp found by scrubbing it by eye, or a different, better-behaved calibration clip.
- `tools/posture-video-player.html` would not open at all in Safari on the real Mac, immediately after being introduced (see "Continuous video tracking" above). Root cause: the page loaded `scripts/lib/render-skeleton-overlay-svg.cjs` via `<script src="../scripts/lib/render-skeleton-overlay-svg.cjs">` — a relative path that walks UP out of `tools/` into a sibling folder. Chrome had shown no problem with this (which is how it wasn't caught before), but Safari's `file://` security sandbox refuses to load a subresource from a directory above the page's own folder. Fixing this properly (e.g. serving the package over a local HTTP server) would break the project's "just double-click the file, no dependencies" design for this tool, so the fix instead copies the same rendering functions directly into `posture-video-player.html`'s own inline `<script>` block — the identical tradeoff already made deliberately for `tools/overhead-alignment.html`'s math helpers. `scripts/lib/render-skeleton-overlay-svg.cjs` itself is unchanged and still the one `inspect-posture.cjs` actually uses via `require()`; only the browser copy moved. Its dual-environment `module.exports` guard is left in place (harmless, and would still matter if some future browser tool is served over real HTTP rather than opened as a local file) but nothing currently depends on it working in a browser.
- Separately, once the page did open in Safari, both the Kim Woojin calibration video and a real phone video the user uploaded directly rendered the player noticeably small, regardless of the source video's actual resolution. Cause: `<video>` and `#overlay` inside `.video-wrap` are both `position: absolute`, which removes them from the page's normal layout flow — an absolutely positioned element contributes nothing to its ancestors' size. The plain `<div>` wrapping `.video-wrap` (a flex item inside `.layout`, no explicit width of its own) therefore had nothing real to size itself from and collapsed toward the flex row's minimum, which `.video-wrap`'s `width: 100%` then inherited — a small width regardless of the video's own pixel dimensions. Fixed by giving that wrapping `<div>` its own class (`.video-panel`) with a real `flex-basis` (`flex: 3 1 640px; min-width: 480px; max-width: 1200px`), so it actually claims real horizontal space in the row instead of shrinking to its (size-contributing-nothing) children.
- With the player now visibly full-size, the skeleton overlay itself looked wrong on real footage — points not corresponding to where the archer's body actually is. Two separate real causes, found by checking exactly what the user had loaded, not assumed: (1) the user tested their own phone video (`IMG_1259.mov`) while the JSON file selector still had the Kim Woojin calibration clip's timeline loaded — a completely different video's keypoints overlaid on unrelated footage will, correctly, look placed at random, since nothing in this page ever checks that the two files actually correspond to each other. Added a real check for this: `checkDimensionMismatch()` compares the loaded `<video>`'s real `videoWidth`/`videoHeight` against the JSON's `widthPixels`/`heightPixels` (and its recorded `videoFileName`, if present) whenever either file changes, and shows a visible red warning banner instead of silently rendering a meaningless overlay. (2) Independent of that, a real alignment bug regardless of which video/JSON pair is used: `<video>` (styled `width:100%; height:100%`) and the overlay `<svg>` (same styling) each individually decide how to fit their own content into that box, and SVG's specified default (`preserveAspectRatio="xMidYMid meet"`) letterboxes to preserve the `viewBox`'s own aspect ratio whenever it differs from the rendered box's — a different amount of letterboxing than the video layer would apply, silently drifting the two out of alignment whenever the container's aspect-ratio (taken from the JSON) doesn't exactly equal the video's own. Fixed by making both layers stretch identically instead of each independently deciding how to fit: explicit `object-fit: fill` on the `<video>` CSS, and `preserveAspectRatio="none"` added to the SVG root emitted by `renderSkeletonOverlaySvg()` — kept in sync between the inline copy in `posture-video-player.html` and `scripts/lib/render-skeleton-overlay-svg.cjs` (the latter is far less exposed to this specific bug, since its one caller, `render-posture-overlay-html.cjs`, always pairs an SVG with the exact same still frame it was computed from — but the two copies are kept identical rather than left to silently diverge).
